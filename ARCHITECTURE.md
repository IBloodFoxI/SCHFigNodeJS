# Как это устроено и почему именно так

Объяснение для тех, кто вернётся к этому коду через полгода — включая меня.

## Задача

Дать аватары Figura на сервере, где играют вперемешку лицензионные игроки и
пиратки, и заодно снять лимит веса аватара в 100 КБ.

Официальный бэкенд Figura не подходит по обоим пунктам: он привязан к
авторизации Mojang и лимит там фиксированный.

## Почему одного сервиса мало

Первое, что хочется сделать — поднять свой бэкенд и переключить на него клиентов.
Не работает: **два блокера сидят в самом моде**, и никакой бэкенд их не обойдёт.

### Блокер 1 — авторизация

`backend2/AuthHandler.java` в клиенте:

```java
String serverID = getServerID(username);                       // запрос к бэкенду
minecraft.services().sessionService().joinServer(...serverID); // запрос к Mojang
NetworkStuff.authSuccess(getToken(serverID));                  // снова к бэкенду
```

Клиент сам дёргает сессионный сервер **между** двумя обращениями к бэкенду. У
пиратки `joinServer` кидает `InvalidCredentialsException`, и до третьей строки
дело не доходит вообще. Обрыв происходит на клиенте, сервер об этом даже не
узнаёт.

### Блокер 2 — фильтр UUID

`backend2/NetworkStuff.java`:

```java
private static boolean checkUUID(UUID id) {
    if (id.version() != 4) { /* voiding request */ return true; }
```

Стоит на `getUser`, `getAvatar`, `sub`, `unsub`. Offline-UUID — третьей версии
(`md5("OfflinePlayer:<ник>")`), а не четвёртой. То есть аватар пиратки никто бы
даже не попытался загрузить.

### Вывод

Нужен форк клиента. Он есть — **SCHFigura**, шесть правок и два новых класса.

## Три части системы

```
SCHFigura (форк клиента)      FiguraLink (плагин Paper)     figura-backend (этот репозиторий)
────────────────────────      ─────────────────────────     ─────────────────────────────────
пропускает joinServer         игрок зашёл и прошёл nLogin   HTTP /api/* и вебсокет /ws
снимает фильтр UUID             ↓                           хранит аватары и профили
принимает figura:backend  ←── подписывает HMAC-токен        проверяет подпись токена
   ↓                          отправляет пакет              лимиты читает прямо из токена
ходит на бэкенд по токену                    └─── общий секрет ───┘
```

## Почему бэкенд отдельным сервисом

Изначально всё было одним плагином Paper. Разделили, потому что так лучше:

* **аватары переживают рестарт игрового сервера** — раньше при перезапуске они
  отваливались у всех;
* **сервис можно унести на другой хост** (например, туда, где уже живёт сайт с
  доменом и сертификатом) — тогда поддомен не указывает на игровой сервер и IP
  не светится;
* TLS настраивается там, где его уже умеют готовить.

## Что осталось в плагине и почему

Только выдача токена. Это единственное, что физически обязано быть внутри
Minecraft-сервера:

* только там известно, кто скрывается за ником **после** nLogin;
* только оттуда можно отправить пакет по plugin channel.

## Токены: почему stateless

Токен — это `base64url(payload).base64url(hmac_sha256(secret, payload))`, где
payload это склеенные через `U+001F` поля: uuid, ник, срок годности и лимиты
игрока.

Из этого следует всё остальное:

* **бэкенду не нужна база** — он читает лимиты прямо из подписанного payload;
* **не нужен порядок запуска** — плагин и сервис могут стартовать в любом
  порядке и вообще не знать друг о друге;
* **не нужна сеть между ними** — они не общаются, вообще никогда;
* **работает на сети из нескольких Paper-серверов** — токен, выданный любым,
  примет тот же самый сервис;
* **язык не важен** — изначально проверка была на Java, теперь на TypeScript, а
  подпись как была, так и осталась.

Плата за это одна: **токен нельзя отозвать до истечения срока**. Поэтому не
ставьте `token-ttl-minutes` в неделю.

## Почему лимит веса задаётся в плагине, а не здесь

Лимит зависит от группы прав игрока, а про группы знает только Minecraft-сервер.
Поэтому плагин вшивает лимит в токен, а сервис его оттуда читает.

В `.env` есть `FIGURA_MAX_AVATAR_SIZE_CEILING` — это **не** рабочий лимит, а
предохранитель на случай сломанного или устаревшего плагина. Ставьте его заметно
выше плагинного и забудьте.

## Почему TLS обязателен

Клиент строит адреса так:

```java
"https://" + getBackendAddressWithPort() + "/api"
"wss://"   + getBackendAddressWithPort() + "/ws"
```

Схемы зашиты в код мода, открытый HTTP он не умеет в принципе. Самоподписанный
сертификат тоже не подойдёт: `java.net.http.HttpClient` проверяет цепочку по
системному truststore.

Отсюда же требование, которое ломает половину конфигов nginx: **`/api/` и `/ws`
обязаны идти на один и тот же порт**, потому что клиент собирает оба адреса из
одной строки.

## Почему сервис пингует вебсокеты

`FIGURA_WS_KEEPALIVE_SECONDS`. Соединение Figura простаивает, пока никто не шлёт
Lua-пинги, а Cloudflare и nginx рвут простаивающие соединения. Пинг раз в 30
секунд держит их живыми и заодно вычищает мёртвые сокеты.

За Cloudflare не выключайте.

## Почему токен выдаётся после nLogin, а не при входе

Offline-UUID выводится из ника. Значит токен, выданный человеку, который просто
стоит на экране логина под чужим ником, позволил бы ему **перезаписать чужой
аватар**.

Плагин ждёт `nLoginAPI.getApi().isAuthenticated(ник)`, опрашивая раз в секунду.
В первой версии этой ошибки не было видно, потому что токен выдавался на
`PlayerJoinEvent` — то есть до авторизации.

## Как это тестируется без Minecraft

Токены stateless, значит их можно подделать, зная секрет. Два скрипта на чистом
Python (`wstest.py` собирает WebSocket-кадры руками, без зависимостей) гоняют
весь протокол под **offline-UUID третьей версии** — тем самым, что получает
пиратка:

* загрузка аватара на 150 КБ проходит, на 600 КБ отклоняется по лимиту;
* `/limits` отдаёт то, что вшито в токен, а не зашитые 102400;
* equip, профиль с верным sha256, скачивание байт-в-байт, удаление;
* вебсокет: авторизация, ретрансляция пингов подписчикам, отписка, лимит размера.

Отдельная и самая важная проверка — **токен, подписанный Java-плагином,
принимается этим сервисом**. Только она доказывает, что две реализации сошлись в
формате:

```bash
java -cp FiguraLink-1.0.0.jar dev.figura.link.Tokens <secret> <uuid> <ник> 512000
curl -H "token: <токен>" http://127.0.0.1:8080/api/limits
```

## Протокол backend2 вкратце

Всё выяснено чтением исходников Figura ветки `1.21.11`, а не документации —
её на этот счёт нет.

HTTP, база `https://<адрес>/api`, заголовок авторизации называется `token`:

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/limits` | `{"rate":{...},"limits":{"maxAvatarSize":N}}` — вот где снимается 100 КБ |
| GET | `/<uuid>` | профиль: надетые аватары с хэшами и значки |
| GET | `/<owner>/<id>` | байты аватара |
| PUT | `/<id>` | загрузка |
| DELETE | `/<id>` | удаление |
| POST | `/equip` | надеть аватар |
| GET | `/version`, `/motd` | версия и сообщение в гардеробе |
| GET | `/assets/<version>[/<путь>]` | значки и эмодзи, проксируются и кэшируются |
| GET | `/auth/id`, `/auth/verify` | резервный путь через Mojang для немодифицированных клиентов |

Вебсокет `wss://<адрес>/ws`, только бинарные кадры:

* C2S: `TOKEN=0`, `PING=1`, `SUB=2`, `UNSUB=3`
* S2C: `AUTH=0`, `PING=1`, `EVENT=2`, `TOAST=3`, `CHAT=4`, `NOTICE=5`

Пинг игрока ретранслируется всем, кто подписан на его UUID, кроме него самого —
автор уже выполнил пинг локально, эхо запустило бы его дважды. `EVENT`
рассылается при смене аватара, чтобы подписчики его перекачали.

## Почему активность считается по токену, а не по скачиваниям

Очистка сносит аватары, которых никто не трогал N дней. Вопрос — что считать
«трогали».

Очевидный вариант — время последнего скачивания — **неверен**. Клиенты кэшируют
аватары по хэшу, поэтому файл человека, который играет каждый день, может
неделями никем не запрашиваться: у всех вокруг он уже есть.

Правильный сигнал — обращения **самого владельца**. Каждый запрос несёт токен с
его UUID, так что сервис отмечает игрока живым на любом обращении и обновляет
mtime его файлов (не чаще раза в час, чтобы не молотить диск).

## Почему удаление идёт через сервис, а не по файлам

У сервиса в памяти живут кэш хэшей и кэш профилей. Если снести файл мимо него —
скажем, `rm` внутри контейнера — профиль продолжит отдавать хэш несуществующего
аватара, и клиенты будут получать 404 на скачивании.

Поэтому ручное удаление сделано маршрутом `POST /api/admin/purge/<uuid>`: он
проходит через те же методы хранилища, что и обычная работа, сбрасывает кэши и
рассылает подписчикам `EVENT`, чтобы те перезапросили.

## Известные ограничения

* Токен нельзя отозвать досрочно.
* Значки хранятся, но выдавать их пока нечем — в профиле пустые массивы.
* Связка «плагин → форк клиента» по plugin channel вживую не проверялась: для
  этого нужен реальный заход в игру. HTTP и вебсокет закрыты тестами.
